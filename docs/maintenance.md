# リポジトリの運用

このリポジトリを運用する人（管理者、またはフォークした人）向けの手順です。

## 構成

```
.github/workflows/release.yml   手動実行（定期実行は任意で追加）。検知、ビルド、テスト、署名、公開、通知
.github/workflows/ci.yml        プルリクエスト用。自動テスト、ビルド、テスト（公開しない）
lib/ubp/                        版番号、パッチの判定、spec と debian の書き換え、署名の検証、リリースの署名、通知、公開
packaging/                      統一オプション（options.json）、rpm と deb の作成、コンテナ内テスト
packaging/keys/                 NLnet Labs のリリース署名鍵 G2、このリポジトリのリリース署名の公開鍵
containers/                     ビルド用とテスト用のコンテナの定義
server/unbound-update           DNS サーバーに置く 1 ファイルのコマンド
tests/                          自動テスト（python3 -I tests/run_all.py）
```

### `release` ワークフローのジョブ

ジョブごとに、必要な権限だけを付けています。ワークフロー全体の既定は読み取り専用です。

| ジョブ | 行うこと | 権限 | 受け取るシークレット |
| --- | --- | --- | --- |
| `detect` | 上流の新版の検知 | `contents: read`、`issues: read` | 通知のステップだけが `DISCORD_WEBHOOK_URL` |
| `build` | 自動テスト、ビルド、パッケージのテスト。成果物を Actions の成果物として保存 | `contents: read` | なし（トークンも渡しません） |
| `publish` | 成果物の取得、`SHA256SUMS` への署名、リリースの公開 | `contents: write` | 署名のステップだけが `RELEASE_SIGNING_KEY` |
| `record` | 成功または失敗の記録（Issue）と通知 | `contents: read`、`issues: write` | 通知のステップだけが `DISCORD_WEBHOOK_URL` |
| `keepalive` | 定期実行の維持 | `actions: write` | `DISCORD_WEBHOOK_URL` |

ジョブの間で成果物を受け渡すため、GitHub 公式の `actions/upload-artifact` と `actions/download-artifact` だけを、コミットの SHA で固定して使います。ほかの外部のアクションは使いません。成果物は 7 日で消えます。

## 流れ

1. `release` ワークフローが、上流の版を調べます。最初は手動で実行します。定期実行は、ワークフローに追加するまで動きません（「定期実行を有効にする」）。
2. 新版があれば、両 OS のパッケージをコンテナでビルドし、テストします。
3. 両方に合格したら、`SHA256SUMS` に署名し、リリースとして公開して、Discord に通知します。
4. ビルドやテストに失敗したら、「ビルド失敗: Unbound 版」という題の Issue に記録し、次の実行でもう一度試します。3 回失敗したら、自動の再試行をやめます。

## 注意事項

- **GitHub のアカウントが、DNS サーバーの入口になります。** 公開したパッケージは、DNS サーバーに root 権限で導入されます。二要素認証を有効にし、`main` を保護してください。
- **このリポジトリは公開されています。** DNS サーバーの IP アドレス、ホスト名、ローカルの名前、Webhook URL を、リポジトリ、Issue、プルリクエストに書かないでください。

## 初期設定

画面の項目名は変わることがあるため、目的を先に書いています。

### Discord の Webhook URL を登録する

目的: 通知先を、リポジトリの中ではなく GitHub のシークレットに置く。

1. リポジトリの「Settings」→「Secrets and variables」→「Actions」を開きます。
2. 「New repository secret」で、名前を `DISCORD_WEBHOOK_URL`、値を Webhook URL にして登録します。

登録しなければ通知しません（エラーにもなりません）。戻すには、このシークレットを削除します。

### Actions の設定を確かめる

目的: 外部の人のプルリクエストが、勝手にワークフローを動かさないようにする。

1. 「Settings」→「Actions」→「General」を開きます。
2. フォークからのプルリクエストのワークフローについて、外部の貢献者すべてに承認を求める設定を選びます。
3. ワークフローの権限の既定を、読み取り専用にします。

`ci` ワークフローは、フォークからのプルリクエストでは動かない条件を自分でも持っています。シークレットは、フォークから起動されたワークフローには渡りません。

### `main` を保護する

目的: 自動化の仕組みや第三者が、`main` を直接書き換えられないようにする。公開するパッケージは `main` からだけ作られます。

1. 「Settings」→「Rules」→「Rulesets」（または「Branches」）で、`main` を対象にした規則を作ります。
2. 次を有効にします。
   - プルリクエストを必須にする（必要な承認の数は 0。管理者自身がマージします）
   - 強制プッシュを禁止する
   - ブランチの削除を禁止する

副作用: 管理者自身も `main` へ直接プッシュできなくなります。戻すには、この規則を無効にします。

### リリースの署名鍵を登録する

目的: 公開する `SHA256SUMS` に署名し、DNS サーバーの `unbound-update` が、リリースの差し替えを検出できるようにする。

1. 手元の安全な場所で、パスフレーズのない ed25519 の鍵を作ります。

   ```
   ssh-keygen -t ed25519 -N "" -C "unbound-packager release" -f unbound-packager-release
   ```

2. 「Settings」→「Secrets and variables」→「Actions」で、名前を `RELEASE_SIGNING_KEY`、値を秘密鍵のファイル（`unbound-packager-release`）の中身全体にして登録します。
3. 公開鍵（`unbound-packager-release.pub` の 1 行）を、次の 4 か所に書き、プルリクエストで出します。
   - `packaging/keys/release-signing.pub`
   - `server/unbound-update` の `RELEASE_SIGNING_KEY`
   - `README.md` と `docs/usage.md` の `allowed_signers` の行
4. 秘密鍵のファイルは、シークレットに登録したら手元から消すか、オフラインの場所に保管します。

自動テストが、4 か所の公開鍵が同じであることを確かめます。シークレットがない、または公開鍵と対応しない場合は、`publish` ジョブが署名の段階で止まり、公開しません。

鍵を替えると、古い鍵を埋め込んだ `unbound-update` は、新しいリリースの署名を確かめられなくなります。各サーバーで、`docs/usage.md` の「導入」の手順で `unbound-update` を入れ直す必要があります。鍵が漏れた疑いがあるときは、すぐにシークレットを削除し、新しい鍵に替えてください。

## 最初のリリース

`ci` が通り、リリースの署名鍵を登録してから行います。

1. リポジトリの「Actions」→「release」→「Run workflow」を開き、そのまま実行します。
2. 終わると、「Releases」に `v1.26.2-1` のようなタグのリリースができ、Discord に通知が届きます。
3. 失敗した場合は、「ビルド失敗: Unbound 版」という題の Issue ができます。Issue に書かれた実行の記録を見て、原因を調べます。

### 定期実行を有効にする

定期実行は、最初は入れていません。ビルドが通る前に毎日失敗して Issue が増えることや、何もしない実行が毎日記録されることを避けるためです。最初のリリースに成功したら、`release.yml` の `on:` に次を加えるプルリクエストを出します（毎日 4:17（日本時間）ごろ。GitHub の混雑で遅れることがあります）。

```
  schedule:
    - cron: "17 19 * * *"
```

あわせて、`tests/unit/test_repo.py` の `test_release_runs_only_when_started_by_hand` を、定期実行を認める内容に直します。止めるには、この 2 行を消すプルリクエストを出すか、「Actions」→「release」で「Disable workflow」を選びます（手動実行もできなくなります）。

## 日常の運用

| したいこと | 方法 |
| --- | --- |
| 同じ版を作り直す（OS 側の修正を取り込む） | 「Actions」→「release」→「Run workflow」で、版を入れ、作り直しにチェックを入れる |
| 版を指定してビルドする | 同じ画面で、版だけを入れる |
| 定期実行を止める | 「定期実行を有効にする」を参照 |

- 作り直すと、ビルド番号が上がります（`v1.26.2-2`、rpm は `2.local`、deb は `+local2`）。
- リリースは削除しません。deb には GPL-3 のパッケージング（`debian/` 以下）が含まれ、バイナリを受け取った人が、対応するソースを必要な期間入手できるようにする義務があるためです（GPL-3 第 6 条）。各リリースに、バイナリと同じ場所でソースパッケージを置いています。
- 失敗の記録（Issue）は公開されます。内容はビルドのログの要約です。
- 定期実行を有効にしている場合、**毎月 1 日に「定期実行は動いています」という通知が届きます。** 届かなければ、定期実行が止まっています。GitHub は、公開リポジトリで 60 日間動きがないと、定期実行を自動で無効にします。「Actions」→「release」で有効化し直してください。

## うまくいかないとき

| 症状 | 原因と対処 |
| --- | --- |
| `release` が「パッチ … は … 当て直せませんでした」で失敗する | OS 側のパッチが新しい版と衝突しています。人の判断が必要です。原因を調べ、パッチの扱いを直します |
| `release` が「サブパッケージが欠けています」で失敗する | 上流か OS 側のパッケージングが変わっています。同上 |
| `release` が「パッケージングのライセンスが想定と違います」で失敗する | OS 側のライセンスの表記が変わっています。公開してよい条件かを確かめてから、許可リストを見直します |
| `release` が「シークレット RELEASE_SIGNING_KEY がないため、リリースに署名できません」で失敗する | シークレットを登録します（「リリースの署名鍵を登録する」） |
| `release` が「署名を、リポジトリの公開鍵（…）で確かめられませんでした」で失敗する | シークレットの秘密鍵と、`packaging/keys/release-signing.pub` の公開鍵が対応していません。どちらかを直します |
| 通知が届かない | シークレット `DISCORD_WEBHOOK_URL` を確かめます。毎月 1 日の通知も届かなければ、定期実行が無効になっています |

## 直すときに守ること

- 処理は Python で書き、`-I` で動かす。モジュール名を標準ライブラリと重ねない。
- tar を展開するときは、`./` を取り除き、`..` と絶対パスを拒否する。
- 二重実行はロックファイルで防ぐ。
- ある OS のパッケージがそろっていない版は、公開しない。
- ワークフローの `run:` の中に `${{ }}` を直接書かない（`env:` で渡す）。
- 外部のアクションは、`actions/upload-artifact` と `actions/download-artifact` をコミットの SHA で固定して使うものだけにする。
- ビルドとテストのジョブには、書き込みの権限、トークン、シークレットを渡さない。

変更はプルリクエストで出します。`ci` ワークフローが、自動テスト、実ビルド、パッケージのテスト、`unbound-update` の実地テストを行います。
