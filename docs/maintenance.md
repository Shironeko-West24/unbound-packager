# リポジトリの運用

このリポジトリを運用する人（管理者、またはフォークした人）向けの手順です。

## 構成

```
.github/workflows/release.yml   定期実行と手動実行。検知、ビルド、テスト、公開、通知
.github/workflows/ci.yml        プルリクエスト用。自動テスト、ビルド、テスト（公開しない）
lib/ubp/                        版番号、パッチの判定、spec と debian の書き換え、署名の検証、通知、公開
packaging/                      統一オプション（options.json）、rpm と deb の作成、コンテナ内テスト
containers/                     ビルド用とテスト用のコンテナの定義
server/unbound-update           DNS サーバーに置く 1 ファイルのコマンド
tests/                          自動テスト（python3 -I tests/run_all.py）
```

ワークフローは外部のアクション（`uses:`）を使いません。ビルドとテストのステップには、トークンもシークレットも渡しません。

## 流れ

1. `release` ワークフローが、毎日 4:17（日本時間）ごろに上流の版を調べます。GitHub の混雑で遅れることがあります。定期実行は、有効にするまで動きません（「定期実行を有効にする」）。
2. 新版があれば、両 OS のパッケージをコンテナでビルドし、テストします。
3. 両方に合格したら、リリースとして公開し、Discord に通知します。
4. ビルドやテストに失敗したら、「ビルド失敗: Unbound 版」という題の Issue に記録し、翌日にもう一度試します。3 回失敗したら、自動の再試行をやめます。

## 注意事項

- **GitHub のアカウントが、DNS サーバーの入口になります。** 公開したパッケージは、DNS サーバーに root 権限で導入されます。二要素認証を有効にし、`main` を保護してください。
- **このリポジトリは公開されています。** DNS サーバーの IP アドレス、ホスト名、ローカルの名前、Webhook URL を、リポジトリ、Issue、プルリクエストに書かないでください。

## 初期設定

画面の項目名は変わることがあるため、目的を先に書いています。

### Discord の Webhook URL を登録する

目的: 通知先を、リポジトリの中ではなく GitHub のシークレットに置く。

1. リポジトリの「Settings」→「Secrets and variables」→「Actions」を開きます。
2. 「New repository secret」で、名前を `DISCORD_WEBHOOK_URL`、値を Webhook URL にして登録します。

登録しなければ通知しません（エラーにもなりません）。戻すには、このシークレットを削除します。

### Actions の設定を確かめる

目的: 外部の人のプルリクエストが、勝手にワークフローを動かさないようにする。

1. 「Settings」→「Actions」→「General」を開きます。
2. フォークからのプルリクエストのワークフローについて、外部の貢献者すべてに承認を求める設定を選びます。
3. ワークフローの権限の既定を、読み取り専用にします。

`ci` ワークフローは、フォークからのプルリクエストでは動かない条件を自分でも持っています。シークレットは、フォークから起動されたワークフローには渡りません。

### `main` を保護する

目的: 自動化の仕組みや第三者が、`main` を直接書き換えられないようにする。公開するパッケージは `main` からだけ作られます。

1. 「Settings」→「Rules」→「Rulesets」（または「Branches」）で、`main` を対象にした規則を作ります。
2. 次を有効にします。
   - プルリクエストを必須にする（必要な承認の数は 0。管理者自身がマージします）
   - 強制プッシュを禁止する
   - ブランチの削除を禁止する

副作用: 管理者自身も `main` へ直接プッシュできなくなります。戻すには、この規則を無効にします。

## 最初のリリース

`ci` が通る状態になってから行います。

1. リポジトリの「Actions」→「release」→「Run workflow」を開き、そのまま実行します。
2. 終わると、「Releases」に `v1.26.2-1` のようなタグのリリースができ、Discord に通知が届きます。
3. 失敗した場合は、「ビルド失敗: Unbound 版」という題の Issue ができます。Issue に書かれた実行の記録を見て、原因を調べます。

### 定期実行を有効にする

定期実行は、最初は止めてあります。ビルドが通る前に毎日失敗して、Issue が増えるのを避けるためです。最初のリリースに成功したら、有効にします。

1. 「Settings」→「Secrets and variables」→「Actions」の「Variables」を開きます。
2. 「New repository variable」で、名前を `SCHEDULE_ENABLED`、値を `true` にして登録します。

以後は、定期実行が自動で行います。戻すには、この変数を削除するか、値を `false` にします。

## 日常の運用

| したいこと | 方法 |
| --- | --- |
| 同じ版を作り直す（OS 側の修正を取り込む） | 「Actions」→「release」→「Run workflow」で、版を入れ、作り直しにチェックを入れる |
| 版を指定してビルドする | 同じ画面で、版だけを入れる |
| 定期実行を止める | リポジトリの変数 `SCHEDULE_ENABLED` を `false` にする |

- 作り直すと、ビルド番号が上がります（`v1.26.2-2`、rpm は `2.local`、deb は `+local2`）。
- リリースは新しいものから 5 個を残し、古いものは自動で削除します（`packaging/options.json` の `keep_releases`）。
- 失敗の記録（Issue）は公開されます。内容はビルドのログの要約です。
- **毎月 1 日に「定期実行は動いています」という通知が届きます。** 届かなければ、定期実行が止まっています。GitHub は、公開リポジトリで 60 日間動きがないと、定期実行を自動で無効にします。「Actions」→「release」で有効化し直してください。

## うまくいかないとき

| 症状 | 原因と対処 |
| --- | --- |
| `release` が「パッチ … は … 当て直せませんでした」で失敗する | OS 側のパッチが新しい版と衝突しています。人の判断が必要です。原因を調べ、パッチの扱いを直します |
| `release` が「サブパッケージが欠けています」で失敗する | 上流か OS 側のパッケージングが変わっています。同上 |
| `release` が「パッケージングのライセンスが想定と違います」で失敗する | OS 側のライセンスの表記が変わっています。公開してよい条件かを確かめてから、許可リストを見直します |
| 通知が届かない | シークレット `DISCORD_WEBHOOK_URL` を確かめます。毎月 1 日の通知も届かなければ、定期実行が無効になっています |

## 直すときに守ること

- 処理は Python で書き、`-I` で動かす。モジュール名を標準ライブラリと重ねない。
- tar を展開するときは、`./` を取り除き、`..` と絶対パスを拒否する。
- 二重実行はロックファイルで防ぐ。
- ある OS のパッケージがそろっていない版は、公開しない。
- ワークフローの `run:` の中に `${{ }}` を直接書かない（`env:` で渡す）。

変更はプルリクエストで出します。`ci` ワークフローが、自動テスト、実ビルド、パッケージのテスト、`unbound-update` の実地テストを行います。
